Good project tools exist. Banks mostly can’t use them.

The problem is rarely the software. It is where the software runs, and who else can reach what is stored in it.

The data leaves the building
Project threads end up holding customer names, audit findings and system diagrams. Once that sits in a vendor’s cloud, it is an outsourcing arrangement, and your regulator has rules about those.
The approval takes longer than the project
Vendor risk assessment, data-residency questions, legal review, a cloud register entry. Most teams give up halfway and go back to email and a shared spreadsheet.
The tools you are allowed to use are heavy
What is already approved tends to be a ticketing system built for software teams. Operations, compliance and business teams open it once and never return.

Chai takes the simplest route around all three. It is a small, friendly project tool that you install on a server you already own, behind the firewall you already run.

What’s inside

Chai does a handful of things and tries to do them well. If you have used Basecamp, you will know your way around in a minute.

Every screenshot on this page is the hosted demo, with a made-up bank’s projects in it. Search also finds messages, to-dos, comments and chats across your workspace.

Every project gets the same three tools

To-dos, a message board and a chat, with the people working on it shown at the top. Open any project and you know where to look.

Nobody has to design a workflow or configure a board before they can post their first update.

Messages instead of reply-all

Every project has a message board. Someone posts an update or a question, the discussion stays underneath it, and the person who joins in month three can read how a decision was made.

It is the part of Chai that replaces the long email chain with fourteen people in copy.

To-dos with a name next to them

Each to-do can be given to a person and a due date, so the weekly meeting stops being a round of “who had that one?”

There are no story points, swimlanes or sprint ceremonies. People tick things off, and everyone can see what is left.

A chat for every project, and for anyone else

Each project has its own chat for quick questions. Direct and small group chats cover everything that does not belong to a project.

@mentions bring someone in, messages can be edited, and a quiet dot tells you when there is something new.

You decide who sees what

People are invited by email, sign in with a link sent to their work address, and see only the projects they have been added to. Add someone when they join a project, remove them when they move on.

Because sign-in runs through your own mail server, there are no passwords for Chai to store.

Runs on things your infrastructure team already knows

No container platform to learn and no new cloud account to open. If your bank runs any Java application today, it can run Chai.

A Java runtime
Chai is a Spring Boot app packaged as an executable JAR with embedded Tomcat.
A database
MySQL for a real installation, or SQLite if you just want to look around.
A mail server
Any SMTP relay you already have. Chai uses it to send sign-in links.

  1. 1. Get the code

    git clone https://github.com/zbaloch/chai.git
cd chai

  2. 2. Point it at your database and mail server

    export chai_spring_port=8080
export chai_spring_datasource_url=jdbc:sqlite:database.sqlite
export chai_spring_mail_host=smtp.yourbank.internal
export chai_spring_mail_port=25
export chai_spring_host_url=https://chai.yourbank.internal

  3. 3. Build and run the executable JAR

    mvn package
java -jar target/chaiweb-0.0.1-SNAPSHOT.jar

The full list of settings is in the README. If you would rather not do this yourself, that is what paid support is for.

For the person who has to approve this

Someone in information security or IT risk will be asked whether Chai is acceptable. These are the short answers. The long ones are in the source.

Where is our data stored?
In the database you configure, on infrastructure you control. Chai has no storage of its own anywhere else.
Who can read the code?
Anyone. The source is public on GitHub, so your team can review it before it goes near production. Chai is source-available under the FSL-1.1-MIT licence.
How do people sign in?
With a one-time magic link sent to their email address through your own SMTP server. Chai does not use passwords.
What does it depend on?
Java, Spring Boot with embedded Tomcat, and MySQL. These are common technologies that may already be on your approved list.
What if the project is abandoned?
You still have the source, the licence to change it, and your data in a standard database. Nothing switches off.
Can we change it?
You can modify Chai for permitted uses such as running it internally. The FSL-1.1-MIT licence does not allow offering it as a competing hosted service.

Why I built this

I have spent two decades in banking technology, and for most of that time I have watched capable teams run serious projects out of email threads and a spreadsheet called “tracker final v7”.

It was never because they wanted to. The tool they liked was hosted somewhere they were not allowed to put data, and the tools they were allowed to use felt like filling in a form.

Chai is my attempt at the tool I wanted those teams to have: small enough to understand, pleasant enough that people use it without being told to, and installed where the bank’s data already lives.

Zaheer, maintainer of Chai

Questions people ask

Something missing? Write to hello@chaiprojects.com and a person will answer.

Is the free version limited in any way?

No. There is one codebase and everybody gets all of it. Support customers do not receive extra features, a different build or a higher user limit.

Can we try it before installing anything?

Yes. Create an account and use it for as long as you like. It is the same application you would install.

Should we put real bank data in the hosted demo?

Please don’t. The hosted version exists so you can see how Chai feels. Anything confidential belongs in your own installation, which is the whole reason Chai exists.

What do we need to run it?

A server with Java, a MySQL database, and access to an SMTP server for magic-link sign-in emails. Chai runs as an executable JAR with embedded Tomcat. SQLite works too if you only want a quick look.

How is support priced?

As an annual agreement, sized to your installation. Send a short note saying how many people will use Chai and where it will run, and you will get a written quote back.

Can we start free and add support later?

Yes, and many teams should. Install it, run a pilot with one department, and get in touch when it is heading for production.

Does Chai have chat?

Yes. Projects have their own chats, and people can have direct or small-group chats. Chats support @mentions, editing and search.

Are we allowed to modify it?

The FSL-1.1-MIT licence allows use, modification and self-hosting for permitted purposes, including internal company use. It does not allow offering Chai as a competing hosted service. Each release becomes MIT-licensed after two years; releases made before September 30, 2026 remain under MIT. Read the full licence terms.

Is Chai connected to Basecamp?

No. Chai is an independent project inspired by how Basecamp organises work. It shares no code or design assets with it.
